# Part II — LWR / Godunov PDE model

The continuum (LWR) counterpart to the CTM in [`../ctm`](../ctm): the same
2 km × 2 km Gothenburg study area, the same Greenshields fundamental diagram
family and DeSO gravity demand, but roads are discretised as chains of
finite-volume cells and advanced with a **Godunov scheme** instead of the
CTM's single-cell-per-link update.

Both notebooks fetch their own data through DTCC Core at run time (see the
main [README's data-setup section](../README.md#data-setup)) and write their
figures/animations into the current working directory when run — run them
from inside `pde/` so those land here, or `cd` first. Neither notebook is
wired into `scripts/`; run them directly in Jupyter.

| Notebook | What it does | Outputs (when run) | Cost |
|---|---|---|---|
| `verification_pde.ipynb` | Unit-tests the Godunov scheme on a single road against **exact** analytical LWR solutions: a red-light backward shock checked against the Rankine–Hugoniot jump speed, a green-light rarefaction fan, and a global mass ledger. | `shock_spacetime.png`, `shock_trajectory.png`, `shock_profiles.png`, `rarefaction_profiles.png` | Seconds. On this machine: shock speed matched theory to **0.003%** error, mass conserved to **1e-14** (machine precision). |
| `traffic_model_full_en4.ipynb` | The city-scale dynamic simulation: every road is a chain of Godunov cells (uniform Δx = 30 m ⇒ uniform Δt ≈ 1.4 s after merging OSM's sub-metre shape-point edges into super-edges ≥ 35 m), junctions use the Lebacque demand/supply rule, and demand is a gravity model between DeSO zone centroids (production ∝ population, attraction ∝ employment) ramped over a 3-minute morning-peak build-up, T = 1200 s total. | `gothenburg_load.gif`, `gothenburg_speed.gif`, `gothenburg_queue.gif`, `gothenburg_total_delay.png`, `gothenburg_load_histogram.png` | ~12–45 s (864 steps), depending on hardware. On this machine: 4236 raw OSM edges → 491 super-edges, 86% of segments use a tagged OSM `maxspeed` (the rest fall back to per-class defaults), final state reaches 130 jammed super-edges (load > 0.8) and 3207 vehicle-equivalents of delay. |

**Note on `maxspeed`:** unlike the CTM in `ctm/`, where every script builds
`maxspeed=[None]*...` before calling `from_dtcc` (see the CTM README's Known
issues §3), `traffic_model_full_en4.ipynb` *does* read the OSM `maxspeed_kmh`
attribute per segment (`_num(ms0[i], np.nan)` in the graph-loading cell) and
only falls back to the class-default table where the tag is missing. The two
parts are not calibrated identically — this is worth flagging in the report
if the two models' speed fields are compared directly.

**Provenance / recovery note:** both notebooks were originally supplied
without any cell outputs retained in this repository (matching the same
policy the rest of this repo uses for generated PNGs/GIFs — see the root
`.gitignore` — so no embedded image blobs are committed here; re-run a
notebook to regenerate its figures). During packaging, the two source files
were reconstructed cell-by-cell from a verbatim read taken moments before an
accidental local overwrite of the original downloads; both were then
re-executed end-to-end against live DTCC Core data as a check, and every
printed diagnostic (edge/super-edge counts, DeSO totals, final congestion
numbers) matched the originally captured output exactly. Source code and
markdown are intact; only the previously-saved output artifacts (plots,
GIF thumbnails, exact execution counts/metadata) could not be recovered
byte-for-byte and were regenerated by re-running.
